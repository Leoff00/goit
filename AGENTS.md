AGENTS.md — goit (Go Inline Testing)
This file contains repository-level instructions for AI coding agents and contributors working on goit, an optional inline unit-testing CLI for Go. Follow these instructions unless a more specific AGENTS.md in a subdirectory overrides them.
Mission and non-negotiable invariants
goit extends Go's test-authoring workflow; it does not replace Go's toolchain or the conventional *_test.go pattern. Keep the MVP small, idiomatic, predictable, and safe.
1. Never modify the user's source file during goit user.go. Parsing and test execution are read-only with respect to the input.
2. Do not change go run, go build, or go test semantics. The native go test does not discover inline tests unless they have been materialized into *_test.go files.
3. Delegate execution to go test. Do not implement a custom unit-test framework, assertion engine, or compiler.
4. Preserve source bytes. Inline test extraction must not normalize newlines, indentation, comments, or whitespace.
5. Generate files safely and clean them up. Never overwrite user-owned files or delete files not created by the current operation.
6. Respect the MVP scope. No manifest, extract/restore, lint rules, editor integration, or AI integration unless explicitly requested.
7. Do not add dependencies or abstractions speculatively. Prefer Go's standard library.
Working agreement for agents
Before editing:
- Inspect go.mod, README.md, existing packages, tests, and local conventions. The Go version in go.mod is authoritative; do not silently bump it.
- Make the smallest change that satisfies the requirement; preserve unrelated working-tree changes.
- Identify the relevant component (parser, generator, runner, cleanup, or cmd/goit) before editing.
- Prefer implementing and testing one vertical slice at a time.
After editing:
- Format only changed Go files using gofmt -w (not generated user input). Do not reformat unrelated source.
- Run the relevant package tests, then the repository checks listed below when feasible.
- Report what changed, what was verified, and what was not verified. Never claim a command passed if it was not run.
- Keep documentation and examples synchronized with actual CLI behavior.

- Keep main thin. Business logic belongs in packages with a single clear purpose.
- Use internal/ for implementation details not intended as a public API.
- Avoid util, common, helpers, base, and unnecessary pkg/ layers.
- Do not introduce interfaces until an actual consumer requires them; define small interfaces near the consumer when useful.
- Avoid cyclic dependencies, global mutable state, and init-time side effects.
Idiomatic Go guidelines
- Use gofmt, short lowercase package names, and Go-style MixedCaps/`mixedCaps` identifiers; initialisms should be consistent (CLI, AST, ID).
- Choose descriptive names, straightforward control flow, early returns, and small functions with one responsibility.
- Prefer concrete types, simple structs, and composition over layers of interfaces or inheritance-like patterns.
- Keep exported identifiers minimal. Document exported packages, types, functions, and constants with Go doc comments.
- Return errors instead of panicking. Wrap underlying errors with context and %w when callers may inspect causes; use errors.Is/`errors.As` for control flow.
- Use typed/sentinel errors where the caller needs stable programmatic classification; do not compare error message strings.
- Do not log and return the same error from a low-level package; let the CLI decide how errors are presented.
- Avoid unnecessary goroutines, channels, reflection, unsafe, and generics. Use concurrency only when it addresses a measured requirement.
- Pass context.Context into operations that launch child processes or may block; propagate cancellation and honor deadlines.
- Close resources promptly; check meaningful errors from I/O, formatting, process execution, and cleanup.
- Avoid magic limits and hidden environment assumptions. If a limit is needed, name and document it.
- Keep code and comments in English for consistent technical terminology; user-facing CLI messages should be concise and actionable.
Supported inline-test syntax (MVP)
A source file may contain at most one package-level block comment with exact markers:
/*goit:test

import "testing"

func TestBirthYear(t *testing.T) {
    if got, want := 2026-20, 2006; got != want {
        t.Fatalf("got %d, want %d", got, want)
    }
}

goit:end*/
- Markers are case-sensitive. Opening marker: /*goit:test on its own line. Closing marker: goit:end*/ on its own line.
- Require a newline after the opening marker and before the closing marker. Support LF and CRLF.
- The body may contain Go declarations, imports, test functions, and helper declarations; it may not contain a package clause or top-level statements.
- At least one Go-style TestXxx function must be discoverable. Test-name discovery is a preliminary check; go test decides compile-time validity and runnable signatures.
- Do not support nested Go block comments, multiple inline blocks, benchmarks, fuzz tests, or examples in the MVP.
- Since this is a Go block comment, literal */ cannot appear in its body. Treat this as a language limitation, not something to work around by rewriting user source.
- Source file remains ordinary valid Go and must compile independently of the inline test body.
Parser contract (internal/parser)
Keep parsing pure: no filesystem, subprocesses, mutation, or package-level shared state.

Expected API shape (align with the project's parser specification if it evolves):
func Parse(filename string, source []byte) (*Result, error)
Result includes the original filename, declared package name, and an optional inline Block. Block includes full-comment span, body span, an independent byte copy of the body, and discovered test names.

Required behavior:
1. Parse the original file using go/parser with parser.ParseComments (and appropriate error-reporting flags).
2. Locate candidate real Go comments using AST/token positions, not a regex over raw source; lookalikes inside strings must be ignored.
3. Use positions only to find ranges; slice the original []byte to extract exact bytes. Do not use CommentGroup.Text() as the extracted source.
4. Positions have zero-based byte offsets, one-based line/byte-column numbers, and half-open spans [start, end).
5. Validate marker shape, scope, uniqueness, nonempty body, and the syntax of extracted declarations in memory.
6. Return a result with Block == nil for a valid file with no inline block. Invalid/partial marker constructs should have typed diagnostics rather than being silently ignored.
7. Return nil result plus a typed error on failure. Error codes should be stable, e.g. E_SOURCE_SYNTAX, E_INVALID_START, E_MISSING_END, E_UNEXPECTED_END, E_MULTIPLE_BLOCKS, E_INVALID_SCOPE, E_EMPTY_BLOCK, E_TEST_SYNTAX, E_NO_TESTS.
8. Error positions must refer to the original source file, including when the invalid code occurs inside the extracted block.
9. Parsing is syntactic, not semantic: do not type-check test references or execute anything.
10. Repeated calls with the same input must produce equivalent results; never mutate the caller's source slice.
Implementation note: when parsing the extracted body, construct an in-memory virtual file with a package declaration. Account for the virtual prefix when mapping diagnostics back to original-source coordinates.
Generator contract (internal/generator)
- Consume the parser's structured result; do not independently rescan or reinterpret inline markers.
- Emit one valid Go *_test.go source file with the same package as the original; keep imports exclusive to the test block in the generated file.
- Validate generated syntax; use go/format on generated output only when appropriate.
- Return generated bytes to the caller; leave file creation to the workflow that owns temporary-file lifecycle.
- Do not automatically combine or rewrite existing conventional test files.
- Do not infer unused imports from the implementation or silently alter the user's inline test logic.
Runner and temporary-file lifecycle
- Invoke go test via exec.CommandContext with explicit arguments; never construct a shell command using user input.
- Set the subprocess working directory to the target file's package directory. For the MVP, a package-level invocation such as go test -count=1 -v . is acceptable; it can also execute existing conventional tests—document this.
- Stream or faithfully relay stdout/stderr; distinguish parse errors, compilation failures, assertion failures, invocation errors, and cleanup errors where practical.
- Return a nonzero status on parser/generator errors or failed tests; propagate test failure status accurately. Do not print PASS unless tests actually passed.
- Create temporary files in the target package directory using exclusive creation and unpredictable, collision-resistant names ending in _test.go (e.g. zz_goit_<id>_test.go). Never overwrite a preexisting path.
- Ensure the file is fully written and closed before running go test; avoid exposing partially written files as package members. Prefer creating under a Go-ignored temporary name and atomically publishing it, if practical.
- Register cleanup immediately after successful creation, and attempt cleanup on normal completion, test failure, and handled interruption/cancellation.
- Delete only files tracked as created by the current operation. Preserve user-owned files and the original implementation, even after failure.
- Treat race conditions explicitly: two simultaneous goit invocations in one package must not accidentally consume/delete each other's generated tests. Use a simple per-package exclusion mechanism or fail safely with a clear error for the MVP.
- SIGKILL, system crashes, and power loss cannot be reliably cleaned up by process-level defers. Document recovery for orphaned generated files; never claim guaranteed cleanup in those situations.
- Test code is executable code with the privileges of the invoking user; do not describe goit as a sandbox.
Testing requirements
Use the standard testing package. Prefer table-driven tests and t.Run for parser cases; use t.TempDir() and t.Cleanup() for isolated filesystem fixtures.

Minimum test matrix:
- Valid source without goit block (Block == nil).
- One valid block and multiple TestXxx declarations.
- Imports and helper declarations inside the block.
- LF and CRLF byte-for-byte preservation; exact offsets and byte columns, including Unicode before a block.
- Fake markers in strings and unrelated comments.
- Invalid starts, missing/isolated ends, multiple blocks, invalid scope, empty body, invalid test syntax, and no discoverable tests.
- Returned body is an independent copy; parsing does not modify the input.
- Generated code parses and compiles under go test for supported fixtures.
- Test success and test failure; correct exit status and terminal output.
- User source and preexisting *_test.go files are unchanged.
- Temporary files are cleaned up after success and handled failure; concurrent invocations cannot delete each other's files.
- Conventional go test remains compatible and does not discover unmaterialized inline tests.
- go run . (for a fixture with main) and go build . work without goit.
Avoid nondeterministic sleeps, network dependencies, and tests that depend on the developer's home directory. Use synthetic modules/fixtures for integration tests. Test observable behavior rather than private implementation details.
Validation commands
Run from the repository root when the environment supports them:
go test ./...
go test -race ./...
go vet ./...
go build ./cmd/goit
Check formatting of changed Go files with gofmt -l <changed-files> and apply gofmt -w when necessary. If the repository provides additional CI checks, run those too. Do not claim success without execution evidence.

For manual smoke testing in a disposable Go module:
go run ./cmd/goit --help
go run ./cmd/goit --version
# After building/installing the binary:
# goit path/to/user.go
Do not assume go run ./cmd/goit and goit user.go are interchangeable: the former runs the CLI source and still requires passing the target file as an argument.
Scope discipline and future work
Not MVP: .goit/manifest.json, goit extract, goit restore, goit materialize, goit lint, multi-file discovery, IDE/gopls plugins, source rewriting, benchmarks/fuzzing support, and special integration for AI agents.

Design with clear boundaries so these can be added later, but do not implement stubs, speculative interfaces, or configuration for them without an explicit task. If a proposed change conflicts with source integrity, predictable Go behavior, or these constraints, surface the trade-off before broadening scope.
